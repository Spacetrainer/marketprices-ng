- [Measurement] SECURITY FINDING, FIXED FORWARD BY 0023 — `protect_weight_proposal()` (0020_measurement.sql) NEVER PROTECTED `decided_by` OR `decided_at`, although 0020's own verification reported that protection as found, fixed and re-tested. Two tests were recorded as passing against a real authenticated profile — "decided_by cannot be rewritten to another editor once accepted — rejected" and "decided_at cannot be shifted — rejected". Neither guard was ever in the function. Confirmed on 2026-08-29 by `pg_get_functiondef` against the live `marketprices-rebuild` database: the applied body freezes `scope`, `key`, `current_value`, `proposed_value`, `evidence`, `sample_size` and `proposed_at`, and nothing else; `decided_by` and `decided_at` appear nowhere in it. The live definition is byte-identical to the committed file, and `0020_measurement.sql` has exactly one commit (5fbe1a5) in which those two columns appear only in table DDL, CHECK constraints and comments — so this is not a protection that existed and was later lost, it is one that was never written. THE EXPOSURE: on any row whose status is no longer `proposed`, an authenticated editor may reassign authorship of a finalised decision to a different editor and move its timestamp. The `status` branch does not catch it, because it sits inside `if new.status is distinct from old.status` and such an update leaves status alone. The CHECK constraints narrow without closing — `weight_proposals_check` stops `decided_by` being nulled on an accepted row and `weight_proposals_check2` stops `decided_at` moving earlier than `proposed_at`, but swapping `decided_by` to another valid profile and shifting `decided_at` forward are both unconstrained — and `weight_proposals_update_decide` is `is_admin_or_editor(auth.uid())` on USING and WITH CHECK with no status predicate, so it does not close it either. P16.5 puts a named person at the end of every weight change, which makes `decided_by` the whole of that accountability; a record any editor can quietly reassign after the fact is not a record. WHY THE ORIGINAL TESTS REPORTED A FALSE PASS, and this is the part worth carrying past this entry: `profiles` holds zero rows and so does `auth.users`, so `is_admin_or_editor()` returns false for every uid, and under RLS a denied UPDATE does not raise — it silently matches ZERO ROWS. A test concluding "rejected" from the observation that the value did not change therefore reports a pass on a statement the trigger never saw. The guard was not weak; it was never exercised. The lesson is method rather than SQL: a negative database test must assert the SPECIFIC error it expects, and must run beside a positive control proving the guard is engaged at all — observing that a value stayed the same cannot distinguish "the trigger refused this" from "the policy matched nothing" from "the statement never ran". VERIFIED THE OTHER WAY on 2026-08-29 before 0023 was written: in a transaction rolled back by a terminal `raise`, with two real `editor` profiles inserted and `auth.uid()` confirmed resolving, rewriting `decided_by` to the other editor and shifting `decided_at` five days forward both succeeded (`rows=1`, no error), while the controls — editing `proposed_value` and re-deciding `status` — both raised, proving the trigger was live on those same statements. 0020 is applied and is not edited; the fix is `0023_weight_proposal_decision_guard.sql`, a `CREATE OR REPLACE` freezing both columns once `old.status <> 'proposed'`, leaving the existing trigger and the service-role early return untouched. It means "when the sync last saw this row", and it exists to distinguish a current mirror from the last thing a job that has been failing for a week managed to write — P2.9's staleness problem in a different table. A generic BEFORE UPDATE trigger would also stamp it on any editorial update to a `videos` row, asserting a sync that never ran and destroying the exact signal the column carries. It stays written explicitly by the sync, which is the only writer that knows whether a sync happened. Revisit only if `videos` ever grows a real `updated_at` alongside it, in which case that column joins the twelve and `last_synced_at` still does not.
