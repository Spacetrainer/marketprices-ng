- [Videos] `videos.published_at` is renamed to `youtube_published_at` in 0016_videos.sql, diverging from §9.1's printed column list. `published_at` is not a wrong name for the field — it is a correct name for a different fact, and that is the problem. Across this schema `published_at` already means the moment WE released something to OUR readers (articles.published_at, written by the publish cron and governed by P5.1). On `videos` it would mean the moment a video appeared on the YouTube channel. Those never coincide: a video synced today may have gone up eighteen months ago, and the article carrying it publishes later still on its own schedule. The collision is silent rather than noisy — both columns are timestamptz, both sort descending in a "newest first" list, and a query joining videos to articles can say `published_at` and be answered by either table with no error, only a wrong answer. "Sort the WATCH band by published_at" is a sentence a person could write meaning either one. A comment warning about the ambiguity only helps the person who reads it; a name that cannot be confused helps the one who does not. Also renamed in the same migration, on weaker grounds: §9.1's `duration` → `duration_seconds`, integer, nullable, `> 0` when present — the spec gives a bare untyped name, which is exactly how an untyped `duration` becomes an interval in one reader's head, a "4:31" string in another's and YouTube's ISO-8601 "PT4M31S" in the API response; naming the unit ends that and the conversion happens once at the sync boundary. Revisit only if §9.1 is ever restated, in which case it should adopt both names rather than these columns reverting.

- [Measurement] THREE DEPARTURES FROM §9.4 on `content_performance` in 0019, consolidated here as one entry. (1) `avg_time` is renamed `avg_time_seconds`, the same call and the same reasoning as 0016's `duration` → `duration_seconds`: §9.4 gives a bare untyped name, which is how an untyped average time becomes seconds in one reader's head, minutes in another's and a Postgres interval in a third's. §8.10's ten-minute cap on average read time is a collector rule and a versioned setting, deliberately NOT a constraint on the column, so the raw figure stays representable. (2) `read_completion` and `watch_through` are stored as FRACTIONS bounded 0–1, not percentages, with the unit stated in the column comment. §8.10 writes "read completion at 80% depth", which reads as a percentage, so this is a real ambiguity resolved rather than an obvious reading: 0–1 matches the existing score family across `signals` and the formatting layer multiplies for display, which is the direction of conversion used everywhere else in this schema. (3) `collected_at timestamptz not null default now()` is ADDED, and is not in §9.4's printed column list at all. It is the companion to `collected_for_date` — one says which day the figure describes, the other when we last went and asked — added on the same reasoning that gives `sources.last_polled_at` and `last_error` their place in 0017: without it, a source that is genuinely lagging and a collector that has silently stopped running are indistinguishable, because both present as a newest row describing three days ago. P18.4's freshness statement is answerable from `collected_for_date` alone; telling lag apart from failure is not. It is deliberately excluded from the uniqueness key, since a value that changes on every refresh would make each re-fetch a new row and defeat the key. Revisit all three together if §9.4 is ever restated — it should adopt `avg_time_seconds`, state the fraction convention and print `collected_at`, rather than these columns reverting.
